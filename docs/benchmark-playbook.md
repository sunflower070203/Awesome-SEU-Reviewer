# 跑测评与优化：行动手册

> 配套文档：`CONTRIBUTING.md`（怎么上手）、`benchmark/TASK.md`（跑什么）。
> 本文解决的是**拿到数据之后怎么办**——这是最容易走偏的一步。

---

## 0. 先想清楚：你测的到底是什么

同一份技能文档，在 Codex / WorkBuddy / Trae / Kimi 上表现不同，差异可能来自四个层面：

| 层面 | 例子 | 归谁管 |
|---|---|---|
| **模型能力** | 公式还原准不准、长文档理解 | Agent 厂商 |
| **工具调用** | 会不会主动跑脚本、能不能读图 | Agent 厂商 |
| **上下文管理** | 一次读几页、会不会重复读 | Agent 厂商 |
| **技能本身** | 指令是否清晰、脚本是否好用 | **你** |

**关键判断**：如果**所有 Agent 都失败**，是技能的问题；如果**只有某一个失败**，大概率是那个 Agent 的问题。

**别把 Agent 的短板记成技能的 bug**——这是最常见的误判，会导致你改错地方。

---

## 1. 跑之前：哪些必须一致

| 变量 | 为什么必须一致 |
|---|---|
| **输入文件** | 换一份卷子，所有数字都不可比 |
| **提示词** | 改一个字都可能改变 Agent 的路径选择 |
| **技能 commit** | 不同版本的行为不同，必须记录 hash |
| **图片是否预处理** | 预处理前后 token 差 **73%**，混杂就全废了 |
| **是否重跑 3 次** | 首跑有冷启动，单次结果不可信 |

**记录到 CSV 的 `notes` 列**：`skill@6294d44, preprocessed=yes, scale=1600`

---

## 2. 跑的时候：数字之外还要看什么

CSV 只能记录结果，但**过程**里的信息更值钱。边跑边记这几件事：

### 2.1 它读了几次图？

**这是 token 差异的最大来源**，但不会体现在 CSV 里。

观察方法：看它调用 `Read`/`view_image` 的次数。6 页试卷：

- **6 次**（每页一次）→ 正常
- **12+ 次**（重复读）→ 该 Agent 的上下文管理有问题
- **2 次**（一次读多页）→ 可能漏内容，也可能效率高，要看质量

### 2.2 它在哪一步犹豫/返工？

比如：

> 「这个图我识别不清，能确认一下吗」

**这句话本身是好事**（说明它会求助），但**频率高说明技能缺少"低置信度处理规范"**。

### 2.3 它有没有真的读技能文档？

有些 Agent 会**跳过 SKILL.md 直接干活**，结果用错方法（比如不渲染直接读 PDF 文本层）。

**检查方法**：问它「你按哪份规范做的？」——答不上来就是没读。

## 3. 拿到数据：先分诊，再开药

### 症状 A：token 特别高

**按这个顺序查**：

1. **看 `peak_context_k`** —— 是不是一次性把十几页图全读进去了？
   - 是 → 技能应加「分批处理」的明确指令
2. **看 `input : output` 比** —— 输入占 90% 以上？
   - 是 → 图片成本问题，查分辨率/张数
3. **看是否重复读图** —— 同一步骤读了两遍以上？
   - 是 → Agent 的上下文管理问题，**改技能没用**

### 症状 B：触发失败

**三种情况，原因完全不同**：

| 现象 | 原因 | 对策 |
|---|---|---|
| **完全不触发** | 描述里的关键词没覆盖到用户措辞 | 补触发词（`SKILL.md` 的 `description`） |
| **需人提醒才触发** | 触发词太窄，或 Agent 倾向保守 | 加"应主动使用"的措辞 |
| **触发了但走错分支** | 分支判断规则不清晰 | 改 `SKILL.md` 里的路由逻辑 |

**注意**：第一种和第二种才是技能问题，第三种可能是模型理解能力问题。

### 症状 C：产物质量差

**先分清是「识别错」还是「排版错」**：

- **识别错**（题目文字/公式不对）→ Skill A 的问题
  - 常见原因：分辨率不够、裁剪切掉了内容、公式符号识别偏差
- **排版错**（内容对但位置乱）→ Skill C/D 的问题
  - 常见原因：LaTeX 转义、图片宽度、cls 宏包冲突

**分开统计**（CSV 里 `questions_correct` 和 `figures_good` 是两列），否则不知道该改哪一环。

## 4. 优化的优先级

按**性价比**排序（性价比 = 影响面 ÷ 改动成本）：

| 优先级 | 改动 | 影响 |
|---|---|---|
| **1** | 技能文档里的**流程指令**（分批读图、先试文本层） | 所有 Agent 都受益 |
| **2** | **触发词**覆盖 | 直接决定能不能用上 |
| **3** | **脚本参数默认值**（分辨率、渲染档位） | 影响 token 与质量 |
| **4** | 新增能力（如图形重绘换引擎） | 单个环节 |
| **5** | 针对某个 Agent 的适配 | 只影响一个 |

**反直觉但重要**：**先改文档，再改代码**。

原因：文档改动成本几乎为零，而且能同时影响所有 Agent；代码改动要重新测，周期长。

## 5. 常见误判（会让你改错地方）

### ❌ 把「首跑慢」当成稳定差异

每个 Agent 首次运行都有冷启动。所以：

- **必须跑 3 次取中位数**
- 如果只有 1 次数据，**宁可不下结论**

### ❌ 用一次失败否定整个技能

先看是不是**输入的问题**（图片模糊、格式特殊），再看是不是**那个 Agent 的问题**。

### ❌ 把「Agent 不听话」归因于文档不够详细

有时候文档已经写得很清楚了，是那个 Agent 的工具调用能力弱。
**判断方法**：同一条指令，其他 Agent 能照做吗？能 → 不是文档问题。

### ❌ 优化了一个不重要的指标

比如把 token 从 30000 降到 28000（省 7%），但质量下降 20%。
**永远先保质量**（这条写进了 `docs/token-optimization.md` 的原则里）。

---

## 6. 动改动的纪律

### 一次只改一个变量

改了触发词又改了分辨率，结果变好了——**你不知道是哪个起的作用**。

### 改完必须重跑基线

至少跑一遍**之前表现最好的那个 Agent**，确认没有回退。

### 记录改动的 commit

CSV 的 `notes` 里写 `skill@<commit>`。否则两周后回看，你分不清哪批数据是哪个版本跑的。

### 小步提交

一次改动一个点，commit message 写清楚「改了什么、预期影响什么」。
这样出问题能快速回滚。

---

## 7. 一页速查

```
跑之前：输入/提示词/commit/预处理/3 轮  —— 五项必须一致
跑的时候：读图次数、犹豫点、是否读了技能  —— 三项额外观察
拿到数据：先分诊（token / 触发 / 质量），再开药
优化顺序：文档指令 > 触发词 > 脚本默认值 > 新能力 > 单 Agent 适配
改动纪律：一次一个变量、改完回跑基线、记 commit
```

---

## 8. 如果你只做一件事

**先跑 `benchmark/trigger-cases.md` 那 20 条**。

理由：触发是**一切的前提**。技能再好，不触发就等于不存在。
而且这 20 条成本极低（每条一句话），半小时能跑完四个 Agent。

拿到触发结果后，你会立刻知道：

- 哪类措辞是你的盲区
- 哪个 Agent 最"听话"
- 技能描述是否该重写

**这比一开始就做完整测评更划算。**
